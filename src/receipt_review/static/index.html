这个项目解决什么问题？

把收据图片转换成可核对的商家、地址、日期与总金额，保留每个结果的原文位置，把缺失或歧义交给人处理。第一版建立可运行基线，后续用公开数据检验和改进。

真实业务参考 Ramp 的收据自动化；当前代码是独立实现，没有使用企业内部数据，也不代表 Ramp 的内部架构。

按依赖顺序理解代码

1. 约定数据 → schemas.py、normalize.py

先规定 OCR 行和字段长什么样，再统一金额和日期。证据 ID 连接预测与原文，金额按十进制定点字符串保存。

动手：用两种日期格式构造输入，观察歧义标记；试试金额 12,50 为什么应被拒绝。

2. 从文字找字段 → extraction.py

输入 OCRLine 列表，输出四个 Field。商家用顶部候选，地址用关键词，总金额找 TOTAL 标签，避免把 CASH 实付金额当总额。

动手：把 CASH 改成 200.00，总金额应仍是 12.00；删除 TOTAL 后，应留空而不是猜测。

3. 把不确定交给人 → review.py

检查缺失、低 OCR 分数、多候选、日期歧义和未来日期。OCR 分数不是字段正确概率。所有新票据都进入待复核状态。

4. 保存原始值与修改 → store.py

SQLite 保存原图摘要、原始预测、当前字段与历史。修改时提交 revision，版本过旧返回冲突，避免两个窗口互相覆盖。

动手：同时打开同一票据的两个页面，第一个保存后，第二个应提示刷新。

5. 接入图片模型 → ocr.py

校验格式、大小，旋正 EXIF 图片，调用 RapidOCR CPU 模型，把 SDK 返回结果转换成自己的 OCRLine。替换 OCR 框架只需改适配器。

6. 连成完整用例 → pipeline.py

规范图片 → 摘要去重 → OCR → 抽取 → 风险提示 → 保存。这里负责执行顺序，字段规则仍留在 extraction.py。

7. 让人能用 → api.py、static/index.html

API 接收图片和复核操作，页面展示图片证据和历史。页面不运行字段规则，所有修改都由后端校验后入库。

8. 证明效果 → data.py、evaluation.py、cli.py

公开标注适配器连接 SROIE。标注文字评估只衡量抽取；真实 OCR 评估衡量图片到字段。字段准确率、整单准确率与覆盖率一起看。

9. 守住回归 → tests/

测试重点是金额混淆、日期歧义、重复图片、版本冲突和损坏文件。自制演示只证明流程跑通，不能代替公开测试集效果。

三个指标各看什么？

字段准确率：四个字段逐个比较；空预测也计错。
整单准确率：四个字段必须全对，比字段准确率更严格。
覆盖率：字段是否有输出，不能说明输出是否正确。

日期按日/月/年规范，文本只合并空白和大小写。这里是自定义字段指标，不声称复现竞赛官方评分。

明确不支持的事情

不鉴定票据真伪，不核验税务，不自动付款。第一版没有登录、权限分层、多人身份审计或公网部署。当前主要适配英文/马来西亚收据，中文增值税发票、PDF 和复杂多页票据需要另做数据与规则。

4060 8GB 留给单独 GPU 阶段；当前 CPU 识别不依赖 Dify 或云服务器。
