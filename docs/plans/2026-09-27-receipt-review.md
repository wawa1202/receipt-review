# 票据识别与智能审核：第一版实施计划

目标：在本地完成收据图片上传、真实 OCR、带证据的字段抽取、规则提示、人工复核和评估；CPU 与 GPU 路线分开。

架构方案：RapidOCR 仅负责文字和坐标，自己的业务层负责候选选择、标准化、证据关联、审核状态、版本和评估。FastAPI 提供单机页面，SQLite 保存原始预测和人工修改，图片按内容哈希存储。金额统一 Decimal，不使用浮点数做金额规则。

技术栈：Python 3.12、RapidOCR ONNX Runtime CPU、Pillow、SQLite、FastAPI、原生 HTML/JS、pytest。独立虚拟环境，不修改商品搜索项目。

## 阶段与文件

1. `schemas.py`：OCR 行、字段值、证据行 ID、Issue；拒绝空文本和无效坐标。`normalize.py`：日期日/月约定、金额解析，歧义保留提示。
2. `extraction.py`：规则基线找商家、地址、日期、总金额；总金额不能用最大金额代替；歧义需复核。
3. `review.py`：缺失、低 OCR 分数、语义证据不足、日期歧义和未来日期规则；任何初始预测待复核，不自动付款。
4. `store.py`：内容哈希去重、原预测保留、修改历史、版本乐观锁；同一文件重传不产生两笔记录。
5. `ocr.py`：图片大小/格式验证、懒加载 OCR、OCR 行坐标规范化；模型异常明确报错，不伪造识别结果。
6. `pipeline.py`：图片→OCR→抽取→校验→保存；失败不留下已成功状态。
7. `api.py` 与 `static/index.html`：上传/演示/列表/详情/原图/复核，页面侧栏包括学习路线；证据行可定位，修正要求备注。
8. `evaluation.py`、`data.py`、`cli.py`：字段准确率、整单准确率、覆盖率、逐单错误；预测与标签分离。SROIE 四字段适配，标注文本与真实 OCR 分别标记；先只评估 demo/dev/validation。
9. `tests/`：先写失败测试，再实现上述边界；关键覆盖总金额vs实付、低分、重复提交、版本冲突、无证据值、无效图像、指标错位。
10. `docs/`：案例与来源、选型理由、文件学习顺序、CPU 学习步骤、单独 GPU 计划、面试题、验收证据。

## 第一版验收

- 真 OCR 识别自制演示图片并完成字段复核；单元测试与真实 OCR 烟测分别记录。
- 合成票据只用来验证软件流程，不能把它的准确率当作公开数据集效果。
- 不调用任何云 API，不消费 key，不下载大语言模型，不自动处理付款或报销。
- 不宣称已完成模型微调、真实企业上线或公开 SROIE 独立测试。

## 后续简历验收（不提前声称完成）

CPU：固定 SROIE 来源、许可和样本清单；按文档/商家防泄漏划分；规则与轻量抽取模型对比，分别报告标注文字与真实 OCR 的字段指标；评估复核负担。

GPU：另建训练依赖与目录，在 4060 8GB 实测小模型显存后确定 LoRA 或文档模型路线。对比未训练基线、训练后效果和推理成本。只在开发决策冻结后运行保留测试集。
