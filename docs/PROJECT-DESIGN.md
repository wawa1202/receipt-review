# 项目策划案：票据识别与智能审核

## 1. 从业务问题开始

公开企业案例出处为 Ramp 收据自动化介绍：https://ramp.com/blog/ramp-receipt-automation 。业务目标是减少人工获取和处理收据的工作。本项目选择其中可公开复现的“图片结构化与人工确认”问题，不触碰银行交易、用户邮箱或实际付款链路。

本阶段交付用户：一位需要核对收据字段的人。输入图片，看到四字段及原图依据；有错误可以修正，不丢失模型当时的输出。算法工程学习目标：理解 OCR 错误如何传播、抽取规则如何取舍、质量如何评估、模型如何落到完整工作流。

## 2. 为什么采用这个结构

流程：`api → pipeline → ocr → extraction → review → store`。数据评估：`data → ocr(可选) → extraction → evaluation → report`。

- 适配层与业务层分离：OCR SDK 变化只影响 ocr.py，不应让 UI 和规则重写。
- 值与证据分离保存：Field.value 是候选答案，evidence 是 OCR 行 ID，不把输出文字当作原始证据。
- 原始值和当前值分离：用户修正不等于模型预测正确，评分永远用 prediction，不用人工 current_fields。
- 审核提示与最终状态分离：提示解释不确定性；status 表示人是否完成核对，不能反推“无风险”。
- 推理与评估分离：标签只进入 evaluation，避免无意间把答案喂给规则。

## 3. 数据结构

OCRLine：id、text、bbox、score。bbox 为旋正 PNG 上的轴对齐矩形，像素单位，不是归一化坐标。字段提取器通过 id 引用它。

Field：value、evidence、ocr_score、method、warnings。分数取证据行最低 OCR 分数，是文字识别分数摘要，不是业务字段概率；不能据此声称“99% 准确”。

Document：id、sha256、image_name、prediction、current_fields、status、revision、created_at。prediction 还包含模型版本、抽取器版本、尺寸和耗时。修改 history 记录每次整份字段、状态、备注及时间。

金额以 Decimal 解析，再存标准两位小数字符串。当前无币种字段，不进行跨币种求和或财务对账。日期没有年份时不猜；日/月有歧义时返回提示。商家、地址规则明确是启发式，可能失效。

## 4. 文件内部应该有哪些功能块

|文件|内部功能块|不要混进的逻辑|
|---|---|---|
|schemas.py|常量、数据类、基本合法性|数据库读写|
|normalize.py|金额、日期、文本比较口径|商家候选选择|
|extraction.py|候选正则、证据构造、四字段选择|HTTP 请求、人工状态|
|review.py|提示码字典、证据校验、风险条件|自动批准付款|
|store.py|连接与表初始化、插入去重、详情查询、版本事务|OCR 推理|
|ocr.py|图片限制、方向转换、模型懒加载、格式转换|金额业务规则|
|pipeline.py|互斥、去重检查、顺序执行、保存结果|UI 渲染|
|api.py|请求模型、来源校验、路由、错误状态|重复一套字段算法|
|index.html|侧栏导航、请求封装、原图证据、复核表单、学习页|秘密 key、数据库直连|
|data.py|ID 索引、标注解析、合法性、文件摘要|自动删除异常样本|
|evaluation.py|ID 对齐、规范化、指标、错误列表|使用答案帮助预测|
|cli.py|参数、命令分发、报告元数据|训练代码|

## 5. 当前基线设计的局限

商家取顶部候选，会受广告/税号干扰；地址依赖关键词，续行容易漏；金额需要 TOTAL 标签，复杂表格可能候选错配。两位小数规则不覆盖所有币种。OCR 读序和文字粘连会影响抽取。所有新记录都待复核，因此不能声称已经降低了人工复核率。

首轮错误分析按“文字识别错误 / 阅读顺序 / 候选选择 / 格式规范化 / 标注问题”分类；每次改规则保留原始基线，比较同一冻结开发集。不能只挑修好的票据展示。

## 6. 从第一版到简历项目的验收

|阶段|实物产出|完成标准|
|---|---|---|
|CPU 第一版|可操作页面、源代码、单元/集成测试、自制烟测报告|图片到复核可追溯；失败场景有处理|
|CPU 数据实验|版本化样本清单、划分记录、文本与图片两类结果|公开数据实跑，错误归因，标签无泄漏|
|CPU 改进对照|规则 v1/v2 或轻量学习模型对照、风险分层|同样本比较；不只报告好结果|
|GPU 单独实验|训练配置、训练日志、权重出处、显存/耗时、留出集对照|确有收益或诚实解释失败|
|简历收尾|复现说明、公开可分发样例、演示、数值证据|描述与已实现范围一致|

这些阶段没有承诺预设准确率。不得把下一阶段计划写成完成经历。第一版可以写“实现 OCR 与人工复核流程”，不能写“已完成模型微调并在企业上线”。

## 7. 开源项目适配依据

RapidOCR 的职责只有模型推理，坐标+文本+分数刚好满足证据 UI；ONNX CPU 便于笔记本部署。固定旧版适配器以确保当前环境可复现，升级要验证结果格式和分数变化。

PaddleOCR 是相关 OCR 模型和训练体系的参考；不是再部署一套重复服务。只有错误分析显示文字识别是主要瓶颈时，再评估它的训练路线。

SROIE 团队仓库用来理解四字段与标注格式，不整仓照抄老训练环境。LlamaFactory 目前不加入依赖：它不自动解决票据标注、字段对齐和阅读顺序。LightRAG、FlagEmbedding 与当前四字段抽取闭环没有直接必要关系，不为 star 数堆栈。

当前不接 Dify：增加一个流程服务不能改善字段准确率，反而增加调试链路。以后确有“复核通过后触发通知”的需求，才通过 API 对接；不要把用户原图默认发到云端。
