# 面试问答：按当前实现如实回答

这些覆盖当前项目的主要设计追问，不声称囊括所有面试题。提到训练、公开数据成绩和线上服务时，必须区分已完成与计划。

**1. 项目目标是什么？**
将收据图片转换成四个结构化字段，每个结果能定位到原文；对不确定结果人工修正，保留原预测和修改历史，建立可评估的抽取基线。

**2. 这是不是一个 OCR 接口包装？**
OCR 只产出文字和位置。自己的代码还实现了字段候选选择、日期金额规范化、证据关联、风险提示、精确图像去重、人工复核、版本控制和评估。当前抽取仍是规则基线，尚不能把它描述为已训练的多模态模型。

**3. 为什么参考企业案例却用公开数据？**
企业公开案例证明问题存在，但内部数据与实现不可得。用 SROIE 四字段定义构造可复现问题；不声称拥有 Ramp 数据，也不复刻它的内部系统。

**4. 为什么选 RapidOCR？**
当前需要 Windows CPU 本地推理、文字框和分数；ONNX 适配开销小。业务接口隔离在 ocr.py，后续替换模型时不重写复核流程。选择依据是接口和部署匹配，不是 star 排名。

**5. 为什么不用大模型一次输出 JSON？**
先建立可解释、低成本、可复现基线，知道到底哪里错。生成模型还需处理幻觉、结构合法性、证据、成本与隐私。并非不用大模型，而是先证明升级的收益。

**6. 为什么金额不取最大值？**
实付现金可能高于消费总额，票据也可能包含累计金额。先找到 TOTAL 等业务标签，再选金额候选；缺乏标签就留空或提示人看。

**7. 标签和金额可能不在一个框怎么办？**
规则支持标签后的相邻金额行，但这是有限假设；多列布局、阅读顺序错乱需要几何约束和测试。不能把“相邻”当成任何票据都成立。

**8. OCR 0.99 是否等于字段 99% 正确？**
不是。文字可能识别正确却选到了错误字段，分数也未经过本任务概率校准。当前只作低分提示，所有票据依旧人工复核。

**9. 日期为什么要歧义标记？**
03/04/2024 可以有两种解释。项目默认日/月但不隐藏不确定性；人工以 YYYY-MM-DD 确认，避免静默改变业务日期。

**10. 为什么用 Decimal？**
金额按十进制定点解析，避免浮点表示差异。数据库保存两位小数字符串，比较时使用统一规范。本版本没有币种换算或金额汇总。

**11. 去重能识别同一张票据的重拍照片吗？**
不能。先规范图片再做 SHA-256，只解决像素相同的重复输入。压缩、裁剪、重拍可能产生不同摘要；业务去重需另建单号、商家、日期、金额等规则及误判评估。

**12. 人工改了值，模型评估怎么处理？**
评估用原始 prediction。current_fields 和 history 记录人改后的值，不能混用，否则会把人工劳动算成模型效果。反馈可作为后续标注候选，但需要质检和独立划分。

**13. 两个人同时修改会怎么样？**
当前是无身份的本地单用户应用，但两个窗口也可能冲突。提交带 revision，在 SQLite 事务中检查版本；旧版本返回 409，要求刷新，不静默覆盖。

**14. 为什么用 SQLite，不用 MySQL？**
当前单机、写入量小，需要事务、唯一约束和可靠持久化。SQLite 减少部署成本。多人身份、并发任务和远程服务成熟后再根据负载迁移，不是 SQLite 永远够用。

**15. 图片和数据库能保证原子保存吗？**
当前不能做跨介质原子事务。识别失败不会生成成功文档，但数据库插入失败可能留下图片。工程升级需临时文件、状态机、重试与孤儿清理；不要声称已经实现分布式事务。

**16. 你如何处理不可信上传？**
按实际图片内容校验格式，限制字节和像素，拒绝损坏图和多帧图；随机记录 ID、哈希文件名避免使用原始路径。服务只绑定回环地址，有 Host 和写请求来源校验。尚无账号和完整公网防护，因此不开放公网。

**17. 为什么分 annotation_text 和 real_ocr？**
前者输入人工标注文字，隔离字段抽取能力；后者从原图跑 OCR，评价端到端效果。两种实验口径要标明，否则用干净文字结果冒充线上图片结果会虚高。

**18. 如何避免漏掉失败样本造成高分？**
按文档 ID 严格配对，集合不一致就报错；缺失预测字段计错。不能只评估成功输出的交集，也不能把读取异常静默跳过。

**19. 字段准确率、整单准确率和覆盖率怎么不同？**
四字段对三项，字段准确率 75%，整单准确率 0%；四项都有输出，覆盖率可为 100%。覆盖率不衡量正确性，整单指标更接近是否需要人工改动。

**20. 测试过了是否代表算法效果好？**
不代表。单元测试保护定义好的边界；自制图片烟测验证真实组件能协作；公开冻结测试集才用于估计泛化效果。三者分开记录。

**21. 怎样做防泄漏划分？**
先按文档去重，再考虑商家/模板分组，开发阶段不读保留集来改规则。记录公开预训练模型可能已接触基准的问题；来源与实际文件摘要都要保存。

**22. 如何确定要不要 GPU？**
先看错误分布。OCR 错就评估识别模型适配，布局/字段错就评估字段模型。4060 8GB 先做一小步反向实测显存，不凭参数量保证可训。当前 CPU 闭环无需 GPU。

**23. Dify 在哪里？**
当前没有必要接入。以后若需要复核后的业务通知，可通过 API 编排；Dify 不替代 OCR、标注、字段模型或评估。

**24. 线上需要补什么？**
身份与权限、文件生命周期、异步任务和幂等、失败重试、并发容量、监控告警、数据合规、访问审计和备份恢复。本地 SQLite 历史不等于防篡改合规审计。

**25. 目前能拿出什么证据？**
源代码、自动化测试、真实 CPU OCR 自制样本报告、可操作审核界面。公开 SROIE 留出集和 GPU 训练结果目前尚未完成，不能给面试官编造数字。
